# PaymentFlow large-volume performance results

## Test summary

The suite was executed between 2026-09-07 and 2026-09-08 on one local SQL
Server instance. It covered deterministic data generation, SSIS throughput,
duplicate handling, data reconciliation, report latency, actual execution
plans, index usage, an unsuccessful index experiment, index maintenance and a
database integrity check.

All functional and data-quality checks passed. Performance values apply only
to the environment and workload described below.

## Reporting benchmark at 1,101,000 transactions

Each scenario used one warm-up execution and five measured executions. A
negative change means that the final indexed version was faster.

| Scenario | Baseline average ms | Final indexed average ms | Change |
|---|---:|---:|---:|
| Full year - all filters | 6,721.635 | 6,590.921 | -1.94% |
| Full year - one merchant | 173.449 | 189.645 | +9.34% |
| Full year - Poland and PLN | 4,780.419 | 4,560.944 | -4.59% |
| January - all filters | 789.870 | 758.647 | -3.95% |

The retained covering index improved three broader scenarios. The selective
merchant scenario regressed, but remained below 200 ms on this environment.
The largest report also returned 381,239 grouped rows, so result construction
and transfer are significant parts of its latency.

## Actual execution-plan observations

For the full-year report using the retained index:

- the query scanned 1,101,000 index rows with 5,553 logical reads;
- the plan used degree of parallelism 10;
- measured query CPU time was 8,066 ms and elapsed time was 5,721 ms;
- the memory grant was 421,048 KB, with no grant wait;
- sorting 381,239 aggregate rows was the dominant operator;
- physical reads were zero in the captured warm-cache execution.

These observations explain why a narrower covering index produced only a
modest end-to-end improvement for the largest result set.

## Rejected `TerminalId`-first index experiment

The execution plan recommended an alternative index beginning with
`TerminalId`. The candidate
`IX_PaymentTransaction_TerminalId_OccurredAtUtc` was created and measured, then
removed because it increased report latency.

| Scenario | Retained index average ms | Candidate average ms | Change |
|---|---:|---:|---:|
| Full year - all filters | 6,380.100 | 6,762.923 | +6.00% |
| Full year - one merchant | 184.086 | 217.284 | +18.03% |
| Full year - Poland and PLN | 4,657.595 | 4,735.433 | +1.67% |
| January - all filters | 753.298 | 759.533 | +0.83% |

For the one-merchant plan, the candidate reduced logical reads from 5,553 to
121 and rows read from 1,101,000 to 22,101. It also reduced CPU time from 244
ms to 176 ms. However, the optimizer changed from a parallel plan with degree
of parallelism 10 to a serial plan, increasing captured elapsed time from 127
ms to 176 ms. This demonstrates why a missing-index recommendation must be
validated with workload measurements instead of being accepted automatically.

## Fragmentation and maintenance at 1,301,000 transactions

Randomly distributed transaction dates caused page splits in the reporting
index during the two additional 100,000-row imports.

| Measurement | Before rebuild | After rebuild | Change |
|---|---:|---:|---:|
| Leaf page count | 10,902 | 7,116 | -34.73% |
| Fragmentation | 98.74% | 0.13% | -98.61 percentage points |
| Page-space usage | 58.90% | 90.33% | +31.43 percentage points |

The targeted rebuild used `FILLFACTOR = 90`. It successfully reduced the
index footprint and restored page density. The same-volume latency comparison
was mixed:

| Scenario | Fragmented average ms | Rebuilt average ms | Change |
|---|---:|---:|---:|
| Full year - all filters | 7,477.175 | 7,628.691 | +2.03% |
| Full year - one merchant | 372.255 | 391.923 | +5.28% |
| Full year - Poland and PLN | 5,662.861 | 5,366.016 | -5.24% |
| January - all filters | 841.639 | 900.421 | +6.98% |

The rebuild is therefore classified as storage and maintenance improvement,
not as a guaranteed query-latency optimization. The report remains dominated
by aggregation, sorting and result volume under the warm-cache test policy.

## Integrity check

`DBCC CHECKDB(N'PaymentFlow') WITH NO_INFOMSGS, ALL_ERRORMSGS` was completed
after the imports and index rebuild. The run completed with no errors reported.

## Conclusion

The test run demonstrated that PaymentFlow:

- processes a one-million-row CSV end to end through SSIS;
- rejects repeated transactions without creating duplicates;
- reconciles ETL counters and final database totals;
- preserves positive amounts and complete status history;
- produces parameterized reports over more than one million transactions;
- records reproducible performance measurements and execution plans;
- validates candidate indexes empirically and removes a regressing candidate;
- detects and corrects index fragmentation without overstating its latency
  benefit;
- passes logical validation and the final database integrity check.

## Limitations

- Tests used one local SQL Server instance and synthetic data.
- CPU model, memory capacity and storage type were not recorded.
- Reporting tests used a warm cache and did not test cold-cache behaviour.
- Concurrent users, ETL/report overlap and blocking were not measured.
- The indexed-state ETL runs are scale measurements, not a controlled
  before-and-after index experiment.
